## 1. Production Backend Dockerfile (multi-stage pattern)

Pattern to reinstate at v0.3 (local runtime stays on root `Dockerfile` + docker-compose).

Key stages:
- **`deps`**: `corepack` pnpm; `pnpm install --filter @oceansoft/backend --frozen-lockfile --prod`
- **`build`**: full install (incl. devDeps) → `pnpm --filter @oceansoft/backend run build`
- **`runtime`**: non-root user (`addgroup -S medusa && adduser -S -G medusa -u 1000 medusa`)

**Fix on reinstate**: package name is `@oceansoft/backend` (NOT `@b2b-commerce/backend`); verify Medusa v2 build output path (`.medusa/server`, not `dist/main.js`) before setting `CMD`.

## 2. GitHub Actions Release Pipeline

Tag-only trigger (`on: push: tags: ['v*']`). OIDC role assumption (no long-lived AWS keys).

```yaml
# Minimal pattern (expand at v0.3):
on:
  push:
    tags:
      - 'v*'
jobs:
  release:
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE_ARN }}
          aws-region: ${{ vars.AWS_DEFAULT_REGION }}
      # Build, push ECR, update ECS task definition
```

## 3. ECS Task Definition Pattern

At v0.3, the backend and storefront deploy as separate ECS Fargate tasks on the same cluster. Medusa database migration runs as a one-shot `initContainers` equivalent (ECS run-task with the migration command before the service update).
